[#xactor-drivers]
== Drivers

The scheduler decides what a turn is, and a driver decides when turns happen:
it calls the scheduler's `run_one` until no message is left, or until it has
delivered as many as its host allows. So the same actors run under a plain
loop in a program, one message at a time in a test, or as handlers on a
Boost.Asio strand, and every driver delivers the same messages in the same
order. xactor's drivers are these:

[cols="1,1,3",options="header"]
|===
| Driver | For | What it does

| `fifo_driver`
| A program, native or WASI
| `run_until_idle(log)` delivers until no message is left, and returns how
  many it delivered. `run_turn(n, log)` delivers at most `n`, for a host that
  takes the thread back between turns.

| `test_driver`
| A test
| `step()` and `step(log)` deliver exactly one message, and return whether
  there was one. It has nothing else.

| `asio_driver`
| A native program that runs its turns as Asio handlers
| `run_until_idle(log)`, the same turns posted onto one strand of an
  `io_context` the driver owns. A WASI build leaves it out.
|===

A driver is built over one scheduler, which it holds by reference. The
`log` of `run_until_idle` and `run_turn` is an `xactor::envelope_log*`, and
`nullptr` records nothing; `test_driver` takes an `envelope_log&` in
`step(log)`, and records nothing in `step()`.

`test_driver` is how a test drives actors: each `step` delivers one message,
so after each one the test sees what that message changed, through
`status_of`, `output_of`, `error_of` and `fuel_of`. A test that constructs a
logic itself and hands it to the scheduler's `spawn` can keep a pointer to it
and read its members too, since the scheduler owns the logic and never moves
it. And a log recorded with `step(log)` is compared with the log the test
expects, or with the log of another run of the same input, which must be
equal (<<xactor-testing-actors>>).

[#xactor-drivers-log]
=== The envelope log

The envelope log is the evidence that two runs, or two drivers, delivered the
same messages the same way. `run_one` records an entry for every message it
delivers, before the actor handles it, and nothing for a message that is
dropped:

[cols="1,3",options="header"]
|===
| Member of `logged_envelope` | What it holds

| `sequence`
| The message's sequence number.

| `to`, `from`
| Its receiver, and its sender, 0 for the host.

| `correlation`
| Its execution.

| `remaining_fuel`
| The fuel its execution had when it was delivered.

| `payload_index`
| Which alternative of the message variant it was, its `index()`.
|===

The log keeps which alternative arrived, not the message, so every entry has
the same size and two logs compare cheaply, with `==`. `entries()` returns
them in order. Two schedulers built with the same budgets and fed the same
deliveries record equal logs, whatever driver runs them.

[#xactor-drivers-asio]
=== The Asio driver

`asio_driver` delivers the same turns on Boost.Asio, natively: the turns run
as handlers on a strand of an `io_context` the driver owns, on the thread that
calls `run_until_idle`. The context is the driver's alone: it offers no
executor, so the program's own I/O objects run on a context of their own,
never on the driver's. The driver posts each `run_one` onto the strand and
drains the context with `poll`, which runs what is ready and returns. It never
calls the context's `run`, `run_one` or `run_for`, which would wait for more
work, so a turn never blocks.
